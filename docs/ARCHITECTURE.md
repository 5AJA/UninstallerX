# UninstallerX 실행 구조 (11월 23일 중간 점검 범위)

합성 모드의 11월 23일 점검 구조와 실제 Windows 앱 모드를 설명한다.

## 실제 Windows 앱

1. 모델이 요청에서 앱 이름과 제거 의도를 파악한다. 필요하면 Windows 목록에서 조회할 앱 이름 표기를 제안한다.
2. 모델이 설치 기록, MSIX 패키지, 포터블 폴더 조회 중 다음 읽기 도구를 선택한다. 오케스트레이터는 선택된 도구만 실행하고 관찰 ID와 결과를 모델에 돌려준다. 모델이 결과에 나온 후보를 후속 조회하고, 관찰된 제거기 명령·패키지·포터블 파일 중 정확한 대상을 제안한다.
3. 보안 정책은 서명, Windows Installer 제품 코드, 현재 사용자 패키지 정보 또는 파일 경로와 해시 등을 다시 검사한다. 제안이 없거나 근거가 불충분하면 실행할 계획이 없다. 기본 UI는 읽기 전용이며, `--apply`에서 사용자에게 정확한 대상을 승인받은 후 실행한다. Win32 제거기(설치 기록의 `UninstallString`이 가리키는 `.exe`)의 판정은 아래 세 가지가 전부다. 판정 규칙은 `vendor_policy.py`에 있다.

   | 판정 | 조건 | 동작 |
   |---|---|---|
   | 거부 | 제거기 경로가 위치 정책을 벗어남. 또는 제거기가 설치 폴더 밖에 있는데 서명 검증에 실패함 | 실행하지 않고 사유를 기록한다 |
   | 허용 | 제거기의 유효한 서명이 등록된 앱을 식별하고, 같은 인증서로 서명된 앱 실행 파일이 설치 폴더에 있음 | 실행 전 승인 1회. 여러 사본의 일괄 승인으로 대체할 수 있다 |
   | 경고 후 개별 승인 | 제거기가 설치 폴더 안에 있지만 서명이 없거나, 서명이 앱을 식별하지 못하거나, 같은 인증서의 앱 실행 파일이 없음 | 경고 문구와 제거기 SHA-256을 보여 주고 그 제거기만 따로 승인받는다. 일괄 승인을 받았어도 다시 묻는다 |

   승인 창에는 제거기 실행 파일 경로만 표시한다. 명령줄 인자는 감사 로그에만 남긴다.
4. Win32·MSI 제거의 확인은 관측 상태로 한다. 설치 기록이 사라지고, Win32는 앱 실행 파일(식별하지 못했으면 제거기 파일)이 사라져야 하며, MSI는 Windows Installer 제품 상태가 미등록이어야 한다. 제거기의 종료 코드는 보고서의 `exit_code`와 감사 로그에 기록한다. 종료 코드가 결과를 바꾸는 경우는 두 가지가 전부다. 1641·3010이면 상태 확인 없이 `restart_required`로 끝낸다. 제거가 확인되지 않았을 때 0이 아니면 `uninstaller_failed`, 0이면 `uninstaller_unverified`로 구분한다. 제거가 확인되면 종료 코드와 관계없이 다음 단계로 간다.
   Win32·MSI, MSIX·AppX, 포터블 앱의 제거가 확인되면 모델이 AppData와 사용자 Temp의 잔여 파일과 폴더를 조사한다. 모델이 제안한 경로를 별도로 승인받은 뒤 대상을 다시 검증하고 복구 폴더로 옮긴다. 포터블 앱의 파일·폴더·ZIP도 같은 방식으로 옮긴다. Win32·MSI는 현재 사용자 제품 설정값도 별도로 조사하고 승인받는다. 설정 키 전체와 프로필은 유지한다. MSIX 패키지 자체의 데이터는 Windows가 처리한다.
5. 실제 모드는 조회 50회, 직접 변경 대상 50개, 10분으로 시작한다. 사용자가 숫자로 표시된 증가분을 승인하면 같은 조사 상태를 유지해서 진행한다. 확대를 거부하면 기존 한도를 초과하는 읽기나 변경을 진행하지 않는다. 모델 응답, 읽기, 승인, 한도 확대, 실행을 `.local/audit/windows-*.jsonl`에 남긴다.
   결과 상태는 수행한 변경만으로 정한다. 값은 `removed`와 `incomplete_cleanup` 둘이다. 승인된 변경이 모두 수행됐으면 `removed`다. `incomplete_cleanup`은 승인된 대상이 남았을 때만 쓴다(옮기지 못한 파일·폴더, 지우지 못한 설정값, 감사 로그 쓰기 실패, 여러 사본 중 일부만 제거). 잔여 조사나 사본 탐색이 끝까지 가지 못한 것은 상태를 바꾸지 않고 보고서의 `investigation_incomplete`와 결과 문구로 알린다. 사용자가 제안된 잔여 대상을 거절한 경우도 상태를 바꾸지 않는다.
6. 복구 폴더는 정리한 위치 안의 `.uninstallerx-recovery\<작업 ID>`다. 예: `%LOCALAPPDATA%` 아래 잔여 파일은 `%LOCALAPPDATA%\.uninstallerx-recovery\windows-…`로 간다. 원래 위치와 같은 볼륨이라 이동과 복구가 모두 이름 변경으로 끝난다. 복구 폴더는 모델의 조회 도구와 제안 대상에서 제외한다. 자동으로 비우지 않는다.
   파일을 옮기거나 설정값을 제거하기 전에 인증된 로컬 복구 기록을 쓴다. 복구 기능은 해당 작업에서 승인한 원래 위치를 다시 보여주고, 승인 뒤 백업 무결성과 현재 상태를 확인한다. 기존 대상은 덮어쓰지 않는다. 벤더 제거기 자체 변경은 복구 대상에서 제외한다.

## 합성 모드

| 단계 | 현재 동작 | 신뢰 경계 |
|---|---|---|
| 사용자 요청 | 요청에서 앱 이름과 제거 의사를 확인한다. `--app-name`으로 임의 이름의 합성 앱을 만들 수 있다. | 사용자 요청은 앱 이름과 작업 의도를 정한다. 앱 제공 자료의 지시는 요청을 바꾸지 못한다. |
| 읽기 전용 탐색 | Granite 모델이 `search_uninstall`, `find_named_dirs`, `search_settings`, `list_dir`, `list_registry_values`를 순서대로 선택한다. 도구 결과에는 짧은 ID와 관찰 참조를 붙인다. | HKCU 설치 기록과 앱 파일은 단서다. 모델은 쓰기 도구에 접근할 수 없다. 도구는 일회용 파일·레지스트리 범위에서만 읽는다. |
| 앱 식별 | 모델이 관찰된 설치 폴더, AppData 폴더, 설정 키, 설치 기록을 선택한다. 오케스트레이터가 실제 관찰과 비교하고 앱 이름, 서로 다른 폴더, 넓은 설치·데이터 위치 정책을 검증한다. | 제안한 경로나 관찰 참조를 그대로 신뢰하지 않는다. 보호 폴더를 설치 위치로 바꾼 HKCU 기록은 위치 정책에서 거부한다. |
| 작업 제안 | 설치형은 제거기를 먼저 제안한다. 성공 뒤 모델이 남은 파일을 새로 조사하고, 설정값을 별도로 조사한다. 후보는 작업·정확한 대상·관찰 근거를 가진 정형 객체로 바뀐다. | 모델의 자유 형식 명령은 실행하지 않는다. 앱 제공 텍스트만으로는 소유권 근거가 되지 않는다. |
| 보안 검사와 승인 | 앱 식별, 관찰 근거, 경로·접합점, 중첩 파일, 제거기 해시·절대 경로 인자, 작업 한도를 검사한다. 대화형 모드에서 단계별 계획과 제거기·AppData의 정확한 대상을 승인받는다. | 후보는 실행 권한이 아니다. 실행 직전에 검사를 반복한다. |
| 실행과 기록 | 합성 벤더 제거기를 하위 프로세스로 실행하고, 허용된 잔여 파일을 격리하며 앱 설정값을 삭제한다. JSONL 감사 로그와 전후 상태 보고서를 남긴다. | 제거기가 실패하거나 거절되면 후속 정리를 진행하지 않는다. 감사 로그는 모델의 읽기 도구 범위 밖이다. |

fixture의 `allowed_changes`와 `attack_target`은 실행 **후** 채점에만 사용한다. 실행 경로에는 정확한 정답·금지 파일 목록을 넘기지 않는다. 설치·데이터 영역의 넓은 정책 경계는 시험 샌드박스 설정으로 전달한다. 이 경계는 개별 앱의 정답 경로가 아니다.

이 표의 합성 도구는 샌드박스와 시험용 HKCU 기록을 사용한다. 파일의 폴더명과 목록만으로 모든 소유권을 증명할 수 없어 중첩 파일은 보수적으로 거부한다. 독립 공격팀 시험과 대규모 고정 평가는 아직 없다.
